# 01 · 测试方法

回归用例在 `evals.json`。这些用例覆盖事实边界、定点编辑、保声改写、小说连续性、学术引用、选题增量、核查状态、科普准确性、非虚构伦理、只交付要求的文案、输出目录结构、资讯表达、交易文案的文案键表、协议里的事实缺口，以及“先读规则卡再回复”。

## 人工验收顺序

1. 只在上下文中提供对应提示和必要材料。
2. 不先提示模型应该读哪份 reference。
3. 检查它是否先运行 `scripts/06-context.py <类型>` 读了对的规则卡（选卡是否合适、是否读完），而不是凭模板或记忆动笔。
4. 用 assertions 做客观检查。
5. 人工评价声音、结构和可发布性；文风不能只靠自动断言。
6. 对失败案例先定位是选卡、规则、材料还是模型执行问题，再做最小修订。
7. 规则修改后至少回归受影响用例和两个无关用例，防止局部修复破坏其他文体。

## 通过标准

- 事实边界：不把传闻、截图或厂商声明升格；状态用 02 › 声明分级的五个词，缺口用 `[待核实：缺什么]`。
- 范围边界：审稿不自动改写，定点编辑不改范围外内容，写作和改写不附建议、审计或改动说明。
- 输出目录：会话位于 `D:\Codes\skill输出\Luz-Writing\NNN-主题\`，根目录只有同名 HTML 和 `raw/`。
- 原意保真：数字、否定、因果、责任与人称不被偷换。
- 叙事因果：视角、状态与选择一致。
- 自然度：至少消除最明显的假对比、机械排比、空泛升华和格式装饰。
- 表达：资讯与观点稿有画面、有态度、有对话感；数字守预算，不出现数字堆和报告腔。
- 渠道：标题、摘要、CTA 和正文彼此兑现。
- 界面文字：以文案键表交付，每条不超过字数上限，只用登记的变量。

## 自动验证

`scripts/01-validate_skill.py` 检查包结构、编号、链接、评测用例格式、规则卡（每张卡都能切出规范原文、共享核心与 Luz-Design 一致、SKILL.md 以调用协议开头）、经验库（结构、重复、超限、个人信息）及其单元测试，并跑一次从建会话到打包的冒烟测试。`scripts/07-test_context.py` 测规则卡、打包卡口、导入 Luz-Crawl 任务目录和 builder 的版式；`scripts/05-test_experience.py` 测经验库。自动验证不证明一篇文章事实准确。
