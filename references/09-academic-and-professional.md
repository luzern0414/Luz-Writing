# 09 · 学术与专业写作

## 共同原则

学术论文、研究笔记、方案和内部文档都需要让读者追踪“问题 → 证据 → 判断 → 行动”。专业不等于抽象；每个术语、数字和结论都应能在文档中找到依据。

优先确认：

- 文体、读者、篇幅和提交模板。
- 研究问题或决策问题。
- 已有材料、实验结果、引用要求和数据边界。
- 作者原意、术语与目标期刊/机构规范。
- 哪些内容仍在分析，哪些已经被确认。

## 学术论文

### 主轴

用五段式检查论文故事：

1. 问题是什么？
2. 现有研究/实践缺少什么？
3. 本文用什么方法回答？
4. 哪些证据支持结果？
5. 贡献与限制是什么？

把主轴写成一份 claim–evidence map。摘要、引言、讨论和结论中出现的核心承诺都要在实验结果或理论证据中找到支持。

### 各章节职责

- **摘要：** 问题、方法、数据/实验、关键结果、贡献。
- **引言：** 背景、具体缺口、为何重要、提出的方法、贡献。
- **相关工作：** 按技术或理论主题比较假设、方法与限制，不逐篇流水账。
- **方法：** 假设、变量、流程、算法、复现所需细节、限制。
- **实验：** 数据、平台、参数、指标、基线、重复、不确定性。
- **结果：** 先写发现，再写证据，再解释机制或可能原因，最后说明限制。
- **讨论：** 解释与比较，明确哪些是观察、哪些是推测。
- **结论：** 回答问题、总结证据、说明限制和下一步，不引入未论证的新贡献。

### 段落与流动

一段一个信息。首句告诉读者这一段做什么；后续句子用因果、对照、后果、细化或例子支持。写完每节做反向提纲，确认段落都能回到该节目标。

术语首次出现时定义，之后保持稳定。公式写清变量、单位、假设与适用范围。英文标题、软件名、专有术语和引用条目按原作者与目标规范保留。

### 引用与来源

- 来源身份匹配不等于引文准确。
- 引文或文本已读，不等于来源支持当前论点。
- 支持状态用 [02 · 声明分级](02-evidence-and-fact-checking.md) 的五个词；另记核到了哪一步：只核了身份（作者、年份、DOI 对得上），还是读到了原文与定位。没读到原文的引用最多算“尚未解决”。
- DOI、作者、年份、页码、版本和定位必须核对。
- 参考文献的格式服从目标期刊或机构的模板；没有模板时按 GB/T 7714—2025（2026-07-01 实施，代替 2015 版）。预印本标识为 PP，正文写“预印本”，不当作已发表论文，细则见 [19](19-chinese-text-standards.md) › 参考文献。
- 不能凭记忆补书目字段。
- 对无来源的新增内容使用 `[待核实：缺什么]`。
- 只在读到对应文本和定位后才清除这个标记。
- 检索数据库命中可以作为线索，不能替作者验证论证。

### 学术审校

按四层：

1. **基础：** 主张、理论框架、贡献和证据是否成立。
2. **结构：** 各节是否兑现论文承诺。
3. **段落：** 本段论点与证据是否对应。
4. **句子：** 是否准确表达作者的确定性和概念区分。

用户只要求语言修改时，不擅自减弱学术判断，也不把有意的限定语当成 AI 腔删除。

## 同行评审回复

1. 逐条引用或编号 reviewer comment。
2. 复述你理解的请求，避免答错问题。
3. 说明具体修改位置。
4. 不同意时给文本和证据依据，不攻击评审者。
5. 尚未解决或不属本文范围时直说。
6. 给改变、未改变、未完成三类状态。

## 结构化文档

适用于 PRD、内部方案、规范、决策记录、操作手册和研究简报。交给客户的方案说明书、使用说明、业务逻辑确认表不属于这里，按 [18](18-client-documents.md) 写。

### 先决定文档要完成什么

- 读者要作出决定、执行操作、理解方案，还是留存记录？
- 哪些信息影响决定？
- 哪些是事实，哪些是建议和假设？
- 谁负责、何时完成、如何验证？

### 推荐结构

内部决策和留存类文档：

> 目的 → 背景/现状 → 问题与约束 → 选项 → 建议 → 交付/步骤 → 风险 → 待决事项

可按文体调整，但顺序必须服务于读者决策。客户方案不用这条结构：它先分析客户的需求再给方案，不写价格，不提及其他文件（[18](18-client-documents.md)）。

### 协作写作

大文档按节推进：

1. 收集背景和现有模板。
2. 先写未知最多的核心章节，摘要与背景最后补。
3. 每节确认读者要回答的问题、必须给出的证据和应该删掉的信息。
4. 建立占位骨架，逐节替换。
5. 常用“给五个到二十个候选要点 → 用户选择/合并 → 写段”的方式减少遗漏。
6. 全部完成后做反向提纲、术语统一和读者问题测试。

### 读者测试

根据文档真实用途生成问题：

- 新读者能否找到决定和负责人？
- 能否找出前置条件、成功标准与退出路径？
- 能否复现关键步骤并知道失败怎么办？
- 有没有重复定义、前后矛盾或隐含假设？
- 摘要中的承诺是否都能在正文兑现？

没有独立读者时，模拟一个没有上下文的读者阅读并回答这些问题。不要声称做过未实际执行的外部测试。

## 协议与政策文本

适用于用户服务协议、隐私政策、小程序隐私保护指引、人脸等敏感信息的单独同意书、储值卡与会员卡协议、退款与售后规则、活动与抽奖规则、账号注销说明。

分工：正文由本技能起草或润色；需要哪些文档、展示在哪里、怎样取得和记录同意、版本与重新同意、撤回与注销，由 Luz-Dev 实现。起草可从 Luz-Dev 的协议模板开始，模板只是骨架。上线前由商户确认，建议律师审核；本技能不替商户作法律判断。

### 先拿到事实

- 处理者名称与联系方式、系统实际收集的个人信息字段（以系统数据模型为准）、用途、保存期限、第三方与 SDK 清单、收费与退款规则、适用的门店与服务范围。
- 没有的事实用 `[待核实：缺什么]` 占位，不按常见写法编一个。隐私政策写到的字段必须和系统实际收集的一致。

### 各文档写什么

- **用户服务协议：** 定义与适用范围 → 账号 → 服务内容 → 费用、支付与退款 → 用户的权利与义务 → 服务方的权利与义务 → 个人信息（写明收集原则和用户行使权利的入口；每份协议写完整，不引用其他文件的名称）→ 责任限制 → 协议变更与通知 → 争议解决 → 生效日期与版本号。
- **隐私政策：** 按《个人信息保护法》的告知事项写全：处理者与联系方式；信息种类、目的、方式、保存期限；敏感个人信息的必要性与影响；委托处理、共享与第三方清单；查阅、复制、更正、删除、撤回同意与注销的方式；安全措施；未成年人保护；变更通知方式；生效日期与版本号。
- **小程序用户隐私保护指引：** 在小程序后台填写，结构按微信官方的《小程序用户隐私保护指引内容介绍》：引导语；开发者处理的信息（限于小程序功能所需，平台会按调用的隐私接口预置必填项，并审核处理目的，要求如实填写）；第三方插件；第三方服务商；用户权益（行使查阅、复制、更正、删除等权利的联系方式）；开发者对信息的存储（声明存储期限）；信息的使用规则（超出声明的用途前，要再次弹窗告知并取得明示同意）；信息对外提供（共享、转让、公开披露都要用户的单独同意）；联系方式；可选的补充文档（.txt，最大 100KB）。内容与隐私政策、系统实际调用的接口一致。
- **单独同意书（人脸等）：** 只写这一件事：收集什么、为什么必须、存多久、怎么撤回、不同意时的替代办法；不与其他条款捆绑。替代办法是法定要求：《人脸识别技术应用安全管理办法》（2025-06-01 起施行）规定，存在其他非人脸识别方式的，不得把人脸识别作为唯一验证方式。
- **储值卡与会员卡协议：** 冷静期、余额与次数的退费规则、转让规则、有效期与过期处理、门店停业或闭店时怎么办。
- **活动与抽奖规则、退款与售后规则：** 写法见 [06 · 交易与运营文案](06-marketing-copy.md)；活动开始后规则不再改。

### 法律与标准依据

核对于 2026-11-02；条款号用来回到原文，写进协议正文时用用户看得懂的话，不堆法条。

- 个人信息保护法：告知事项包括处理者名称和联系方式；处理目的、方式、个人信息种类、保存期限；个人行使权利的方式和程序（第十七条）。向其他处理者提供个人信息，要告知接收方的名称或姓名、联系方式、处理目的、方式和信息种类，并取得单独同意（第二十三条）。敏感个人信息（含生物识别、行踪轨迹、金融账户、不满十四周岁未成年人的信息）要单独同意（第二十九条），并告知处理的必要性和对个人权益的影响（第三十条）。处理不满十四周岁未成年人的信息，要取得监护人同意并制定专门的处理规则（第三十一条）。个人有权撤回同意（第十五条）；不能以个人不同意为由拒绝提供产品或服务，处理为提供服务所必需的除外（第十六条）。个人享有知情权、决定权、查阅复制权、更正补充权、删除权，并可要求解释处理规则（第四十四至四十八条）。通过自动化决策向个人推送信息、进行商业营销，要同时提供不针对个人特征的选项或便捷的拒绝方式（第二十四条）。
- 民法典第四百九十六条：格式条款的提供方要遵循公平原则，并以合理的方式提示对方注意免除或减轻其责任等有重大利害关系的条款，对方要求时予以说明；没有做到的，对方可以主张该条款不成为合同内容。不合理地免除或减轻己方责任、加重对方责任、限制对方主要权利的格式条款无效（第四百九十七条）。这是“对用户不利的条款放在显眼位置写清”的依据。
- 消费者权益保护法实施条例（2024-07-01 起施行）：自动续费前后的提醒要求见 [06](06-marketing-copy.md) › 交易与运营文案。
- GB/T 35273—2020《信息安全技术 个人信息安全规范》现行；全国网络安全标准化技术委员会 2026-06 就《数据安全技术 个人信息安全规范》（修订稿）公开征求意见，征求意见期 60 天，写作时未见正式发布，隐私政策按现行版并留意发布。
- 具体行业、平台和地方要求可能更严，以当前官方文本和律师审核为准；本技能不替商户作法律判断。

### 写法

- 用白话写给用户读：一条一件事，短句，先说结果再说条件；术语第一次出现时定义。
- 条款编号连续，互相引用写编号；改写已有条款时，编号、否定、条件、期限和责任主体逐字保留（11 › Gate 3）。
- 对用户不利的条款（费用、自动续费、责任限制、数据共享）放在显眼位置写清，不藏在长段末尾；不写“最终解释权归本公司所有”，不写“以实际为准”这类无法核对的话。
- 每份文档写生效日期与版本号；改版时另写“本次变更摘要”，给需要重新同意的用户看（重新同意的流程由 Luz-Dev 实现）。
- 交付按 15：只交协议正文；需要商户确认的事实留在正文的 `[待核实：…]` 里，对话里一句话说明。

## 专业文字的自然度

- 优先主动句和明确责任主体；法律、实验、制度性表述可以保留被动。
- 一段超过三个并列结构且每项同构时，考虑改为表格。
- 规范、法律和安全限定语是内容，不是套话。
- 操作文档按动作顺序写，写清输入、结果、失败与恢复。
- 文件说明写真实路径、命令、依赖和验证方式。
