# 18 · 客户文件的写法

适用于交给客户的方案说明书、使用说明、业务逻辑确认表，以及这些文件里的每一句话。版式（Word 排版、封面、目录、页眉页脚、表题与续表、黑白）归 Luz-Design；数据结构、门禁和文件分工归 Luz-Project。本篇只写写什么、怎么写、怎么自查。

## 共同写法

- 读者是客户的业务负责人和一线员工，不是工程师。用客户平时说的词：写“顾客预约时段”，不写“调用预约服务接口”。不出现技术栈、库表、接口名和内部编号（FN-001 这类）；必须用的专业词，第一次出现时用客户听得懂的话说明。
- 一份文件把自己的内容写完整，不提及其他文件：不写“详见”“配套文件”“见某某表”，也不写带书名号的文件名。需要的内容直接写进本文件，不靠指向别处来省略。法规名称写成名称本身（个人信息保护法），不加书名号，因为带书名号会被当成文件指引。
- 方案里不写价格、单价、工时和报价，价格只出现在功能清单的报价清单里。双方约定可以写，例如“第三方费用由客户承担”。
- 每个数字有依据：来自客户原始资料、同类系统的调研结论、客户确认过的规则，或者写明“按……估算”的假设。没有依据的数字不写。
- 不留占位文字。草稿里用 `[待核实：缺什么]` 标缺口，交给客户之前全部清掉：补上事实，改成有依据的说法，或请用户确认。待补充、TODO、TBD、xxx、××、【请填写】都算占位。
- 标题短，不加括号说明，不用问句和口号，同级标题概括层级一致。说明放进正文或表题：写“一天的运转”，不写“一天的运转（以午餐为例）”。编号用“一、”“（一）”“1.”“（1）”，四级以内；交给 Word 排版的内容里标题不手打序号，由样式自动编号。
- 正文只用文段、小标题、列点和表格。不用卡片、指标卡、图标、emoji、彩色和装饰。每张表有表题，写在表上方，写内容名，末尾不加句号；长句放进表格前先拆成短句，一格一个事实。
- 规则写边界和数字（“开课前 2 小时可以取消”），不写“支持灵活配置”“按需调整”。做什么、不做什么，都写清。
- 不写自我介绍、阅读指引、客套和自我评价（“全面赋能”“一站式”“行业领先”）。空话按 [17](17-ai-pattern-catalog.md) 换成具体事实。
- 称呼和术语全文统一：同一个东西只用一个名字，“会员”不在后文变成“用户”“客户”。
- 标点、数字、日期按 [19](19-chinese-text-standards.md)。
- 客户新增需求或修改规则时，先在需求变更台账登记，再改文字；只改受影响的章节，不动没变的部分。
- 这些文件交给 Luz-Design 排版成 Word 导出的 PDF（Excel 文件按表格规范）。不要把它们做成阅读型网页，也不配封面插图。

## 方案说明书

必有三章：项目背景与需求分析、解决方案、交付内容；常加建设目标。先分析客户的需求，再给方案：读者读完背景，应当觉得“说的就是我们”，然后才关心怎么解决。

### 项目背景与需求分析

- 业务现状：现状问题表（现状问题 / 具体表现 / 带来的后果）。表现写看得见的事（“高峰期靠群消息登记，容易漏掉”），后果写客户在乎的（漏单、对不上账、顾客久等）。
- 需求分析：按使用方分行（使用方 / 现状与痛点 / 核心需求 / 解决方式）。使用方是顾客、店员、管理者、财务这类真实角色；核心需求用客户自己的话，只写这个使用方真正要的几件事，不替客户编需求。
- 本期需求边界：试点规模，以及本期不做什么。
- 材料来源：客户原始资料（`raw/uploads/`）和对同类系统的调研（Luz-Crawl 前置检索结论）。调研用来写准现状和痛点，来源网址不进客户文件；没有材料支撑的现状不写。

### 建设目标

指标和目标值成对写（指标 / 目标）。目标值来自客户提出的要求或双方确认，写清怎么计算；没有确认的不写数字，不凭行业经验替客户定指标。

### 解决方案

先用一段话写总体思路：针对上面的痛点，分几个系统、各自解决什么。再分小节，小节标题短而并列：

- 系统构成：系统 / 使用者 / 解决什么问题 / 主要功能模块。
- 角色与权限：角色 / 可以做什么 / 不可以做什么。
- 业务流程：环节表（环节 / 谁来做 / 系统做什么 / 结果），再按时间顺序讲一遍“一天的运转”。
- 各系统的功能与业务逻辑：每个系统一张表（功能模块 / 主要功能 / 业务逻辑）。业务逻辑写边界和数字，与功能清单里的规则一致。
- 统一业务规则：几个系统共用的规则（取消、退款、积分、时间限制等），写清每条规则在哪些环节生效。

### 交付内容

交付项 / 内容：交付哪些系统和端、培训、试运行、售后。只写已经确定的，没有确定的时间和数字不写。不写价格和付款节点；费用归属这类约定一句话写明。

## 业务逻辑确认表

先给出拟定的逻辑，再由客户确认或修改，不让客户从零填写。本篇管文字：拟定逻辑、说明与理由、待决定规则的写法，以及需要客户提供的资料怎么问。

- 每个功能一行，拟定逻辑把规则拆成 1、2、3……逐条写，一条一件事，带边界和数字。
- 拟定逻辑写成客户可以直接回答“对”或“改”的句子：“午餐：前一天 15:00 开始报餐，当天 09:30 截止，11:30—13:00 取餐”。
- 每一行都写说明与理由：这条逻辑决定什么、不这样定会怎样。说明写客户看得懂的后果，不写实现方式。
- 业务逻辑项写完整，不写缩略词：写“午餐的报餐和取餐时间”，不写“午餐”。
- 待决定的规则（供餐时间、取消规则、对账周期等）同样给出拟定值。
- 只问只有客户才有的信息（小程序 AppID、域名、首批名单与套餐、试点企业）。企业名称、联系人邮箱、云厂商、操作系统这类每个项目都一样的内容不问。示例写成格式正确、可以照抄的样子（`wx0123456789abcdef`、`meal.example.com`、`周一至周五 6:30—22:30`）。
- 密钥、密码、证书私钥不进表格，只问“已通过安全渠道发送 / 尚未发送”。
- 平台规则（小程序备案、类目资质、支付商户开通材料）只作为向客户确认的问题；具体要求以平台官方最新说明为准，写之前由 Luz-Crawl 前置检索核对。
- “修改后的逻辑”是客户的回答，写作方不预填，也不替客户选“确认”。

## 使用说明

写给每天用系统的人。一章对应一类任务，章标题就是用户要做的事（“预约课程”“处理核销”），不加括号说明。每个在范围内的功能都要出现在某一章里，客户可见的文字不出现功能编号。

- 入口：从哪里进入，用界面上的原文写（“我的 › 预约记录”）。按钮、菜单、状态名与界面一字不差，来源是已确认的界面稿或原型，不凭记忆写。
- 步骤：一步一个动作，祈使句，先写条件和位置，再写动作（“在预约记录页，点击‘取消预约’”）。结果不明显的步骤，紧跟一句结果。可选步骤以“可选：”开头。步骤尽量少，过长就拆成两个任务。
- 规则：写数字与边界（“开课前 2 小时内不能取消”），说明不满足时会怎样。
- 状态：状态名、含义、下一步该做什么，用表格。状态名与界面一致。
- 常见问题：问题用用户会问的话，答案先给结论。只写由功能、规则或试运行反馈得出的问题，不编。
- 角色：按角色分节时，每个功能只在一处讲完整，其他角色需要时写他们在这个功能里能做什么。
- 联系方式：只写真实的支持渠道；没有就不写这一节，不放占位。
- 全文称呼统一（“您”或“你”二选一）；每步用同样的动词写法，同一个界面元素同一个叫法。

## 写进数据文件时

项目模式下，文字写进 Luz-Project 的数据文件，由它的校验把关。写完先自查，再交给它：

- `data/client/requirements.json`：需求说明书，`format` 为 `word`，七章必有：`background` 项目背景（业务现状和按使用方的现状问题表）、`goals` 建设目标、`scope` 范围与使用者、`requirements` 需求清单（每条需求写具体要求和业务规则，功能清单已有时用 auto 块生成）、`rules` 业务规则与约束、`acceptance` 验收标准、`open` 需要客户确认的事项。只写需求，不写解决方案、技术细节和价格；先写现状与问题，再写需求；用客户的词；不提及其他文件。客户有自己的需求文档时不写这份，在 `client_document` 里登记。
- `data/client/proposal.json`：`format` 为 `word`；`hero.info` 写项目名称、版本、日期，不写配套文件；`toc` 为 `true`；`sections` 里 `background`、`solution`、`deliverables` 三章必有，常加 `goals`；块只用 `text`、`sub`、`bullets`、`table`、`matrix`；每张表必须有 `caption`，长文本列用 `widths`；章标题和 `sub` 标题不含括号。`client proposal-draft` 生成的草稿带“待补充”，不能构建，写完要清掉。
- `data/client/manual.json`：每个章节有 `id`、`heading`、`features`、`entry`、`steps`、`rules`；所有在范围内的功能 ID 都被某一章覆盖；含占位文字不能通过。
- 业务逻辑确认表的行由功能清单自动生成；项目专属问题写在 `data/client/intake-extra.json`（`category`、`item`、`kind`、`example`、`why`）。

## 交付前自查

用 `py -X utf8 scripts/09-text_check.py <文件> --doc proposal|manual|confirmation` 先扫一遍，它检查的是下面这些能机器判断的部分，剩下的靠人读：

- 读一遍背景：先写客户的现状、痛点和各使用方的核心需求，再写方案。
- 随机抽三个数字，说出依据。
- 全文搜“详见”“配套”“见……表”、书名号、价格、技术词、占位词，应当为零。
- 每张表有表题；表里没有长段落；每个标题没有括号。
- 把一个业务逻辑读给一位不懂技术的人听，他能说出“对”或“要改”。
- 同一个事实在各章里数字一致（取消时限、名额、时间点）。
