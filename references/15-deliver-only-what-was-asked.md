# 15 · 只交付要求的文案

本规则优先于其他文件里的交付习惯。用户要文案，就只给文案；用户没要的建议、审计、解释、备选和后续计划一律不写。

## 交付什么

| 用户要的 | 只交付 | 不附带 |
| --- | --- | --- |
| 写一篇 / 一段 / 一条 | 成品文案 | 写作思路、结构说明、自评、备选版本 |
| 改写、润色、去 AI 味 | 改后全文 | 改动清单、前后对照、“我删掉了……” |
| 只改某句 / 某段 | 改后的那一句或那一段 | 每处改动的理由、全文其他问题 |
| N 个标题 / slogan / CTA | 正好 N 个 | 推荐哪个、每个的角度说明、打分 |
| 只要一个 | 一个 | “也可以试试……” |
| 审稿、挑问题、诊断 | 问题清单（[11 · 质量闸门](11-quality-gates.md) Gate 8） | 改写全文 |
| 核实某条信息 | 核实结果与状态 | 接下来该查什么、写作建议 |
| 选题、提纲、策划 | 选题或提纲本身 | 成稿、执行计划、风险清单 |

数量、字数、格式、平台、语气以用户原话为准。用户没给数量时给一个。

## 不写的东西

这些内容按类别删除，不论换成什么措辞：

- **开场与收尾客套：** “好的”“以下是为你写的……”“希望对你有帮助”“如需调整请告诉我”。
- **过程说明：** 怎么写的、参考了什么框架、为什么这样安排结构、用了哪个规则。
- **改动说明：** 改了哪里、删了什么、为什么改、保留了什么。
- **未经要求的建议：** “建议配一张图”“可以再加一个案例”“发布时间建议……”“标题还可以……”。
- **未经要求的审计：** 指出原文其他问题、风险评级、合规提示、可读性评分、AI 味评分。
- **备选与扩展：** 多给的版本、A/B 变体、延伸选题、“进阶版”。
- **后续邀约：** “要不要我再……”“我还可以帮你……”。
- **自我评价：** “这版更自然”“更有感染力”“已去除 AI 痕迹”。
- **凭想象补的内容：** 用户和材料都没提供的数据、案例、经历、评价、功能、日期。

## 和事实保真的关系

只交付文案不等于可以编造。缺材料时按这个顺序处理：

1. 能用已有事实写成的，就只用已有事实写，不提缺了什么。
2. 某个说法没有依据，就不写这个说法，而不是在文案外附一段说明。
3. 用户点名要求的内容必须依赖缺失事实时（例如“写上满意度 100%”而没有记录），在文案中用可见缺口 `[待核实：满意度来源]` 占位，对话里用一句话说明缺什么。这是唯一允许的附加说明。
4. 真正阻塞写作的缺口（没有主题、事实互相冲突、要求的引用完全不存在），先问一个问题，不先写一版再附一堆说明。

能合理假设的细节直接按常理处理，不在交付里解释假设。

## 对话中的形式

- 对话回复第一个字就是文案本身，或成品 HTML 的路径。
- 生成了 HTML 时，回复只有路径加用户要的文案（或文案的直接摘录），不复述会话结构、采集过程和检查结果；检查失败或采集阻塞时用一句话说明。
- 多条文案用编号或换行分开，不加“方向一：情感共鸣型”这类角度标签，除非用户要求。
- 不在文案前后加分隔线、加粗标题“改写版本”或引用框。

## 用户明确要了，才给

用户原话里出现“说明一下”“为什么”“给点建议”“帮我看看哪里不好”“审一下”“对比一下”“多给几个”时，相应部分才开放，并且只开放那一部分。一次授权只管这一次请求，不延续到下一次。

## 自检

交付前删掉每一个满足下列任一条件的句子：

1. 用户没要求它。
2. 删掉后文案本身没有损失。
3. 它在评价、解释、建议或预告，而不是文案的一部分。
